# Amazon S3 (and S3-Compatible Object Storage)

## 30-Second Intuition

S3 is a flat key-value store for immutable-ish binary blobs, exposed over HTTP as `PUT`/`GET`/`HEAD`/`DELETE`/`LIST` — not a filesystem, even though every tool built on top of it (`aws s3 cp`, the S3 console, Hadoop's S3A connector) draws a directory tree over it as a UI convenience. The closest comparable systems are DynamoDB (also key-based, also no cross-key transactions) and HDFS (the direct architectural foil — see `storage/hadoop.md`), except S3 has **zero compute/data-locality concept**: every byte you read crosses a network, always, by design, in exchange for storage that scales independently of any compute cluster and durability (11 nines, engineered via internal erasure coding across facilities) that is entirely AWS's problem, invisible to the client. The single fact that matters most operationally, because so much of this KB's own tooling (Iceberg, Delta, Parquet footers) depends on it being true: **since December 2020, S3 provides strong read-after-write consistency for all PUT and DELETE operations, in all regions, with no propagation delay** — the "S3 is eventually consistent" claim you'll still find in older blog posts and even some current tutorials is simply wrong for any AWS commercial region today.

## Resource-Layer Map

| Layer | Role S3 plays | What it's optimizing for |
|---|---|---|
| CPU | Irrelevant on the client side — S3 has no query engine or compute of its own (S3 Select existed as a narrow exception but AWS no longer recommends new adoption of it; the compute is whatever engine — Spark, DuckDB, Trino — sits in front of S3 as a source) | Client-observed CPU cost is 100% a property of the calling engine, not of S3 itself |
| Memory | No client-visible memory model — S3 has no page cache, no buffer pool the client can reason about; any caching (row-group prefetch, footer caching) happens entirely in the calling engine's process | Memory optimization is the caller's job (see `query-engines/duckdb.md`'s HTTPFS prefetch, `data-formats/parquet.md`'s footer caching) |
| Disk | Entirely AWS's internal problem. 11 nines (99.999999999%) annual durability, achieved via redundant storage across a minimum of 3 Availability Zones for S3 Standard, using erasure coding/replication internally — the client never selects a replica, never sees a replication factor, never fscks a block | Contrast directly with HDFS: HDFS's `dfs.replication=3` is a client-visible, client-tunable knob (`storage/hadoop.md`); S3's durability mechanism is not observable or configurable per-object at all |
| Network | **The** resource axis for S3-backed workloads. Every `GET` is a full network round trip; there is no "read local, skip the network" case, ever. What you optimize: request count (each request has fixed per-call overhead, ~tens of ms), range-request byte efficiency (fetch only the Parquet footer, not the whole file), and requests-per-second against a given key prefix (S3 partitions internally by key ranges and can throttle a single unpartitioned prefix under sustained load) | Minimize round trips, maximize useful bytes per round trip, spread request volume across prefixes when sustained rate is high |
| GPU | Not applicable — S3 stores bytes, it has no compute layer; GPU workloads reading training data from S3 are a property of the training framework, not of S3 | N/A |

This is the mirror image of `storage/hadoop.md`'s table: HDFS's whole design point is "move compute to where the replicated data already sits, so the network row stays cheap." S3 has no such option — the network row is unconditionally in the hot path of every read, and S3's entire engineering effort (internal partitioning, request-rate auto-scaling, range-GET support) goes into making that unavoidable network hop as cheap and parallelizable as possible, not into avoiding it.

## The Signature Mechanism: Strong Read-After-Write Consistency

Before December 2020, S3 was documented as **eventually consistent** for overwrite `PUT`s and `LIST` operations (though always strongly consistent for new-object `PUT`s in most regions). On **December 1, 2020**, AWS announced that S3 now delivers strong read-after-write consistency automatically, for every existing and new bucket, at no extra cost, with no configuration required. The current official wording (AWS S3 User Guide, "Amazon S3 data consistency model"):

> "Amazon S3 provides strong read-after-write consistency for PUT and DELETE requests of objects in your Amazon S3 bucket in all AWS Regions. This behavior applies to both writes of new objects as well as PUT requests that overwrite existing objects and DELETE requests. In addition, read operations on Amazon S3 Select, Amazon S3 access control lists (ACLs), Amazon S3 Object Tags, and object metadata (for example, the HEAD object) are strongly consistent."

Concretely, this means:

- A `GET` or `HEAD` immediately after a `PUT` (including an **overwriting** `PUT` to an existing key) always returns the new data — never stale data, never a 404 for a key that was just written.
- A `LIST` immediately after a `PUT` includes the new key (demonstrated in AWS's own docs via example, though not named in the summary sentence above as explicitly as PUT/DELETE are).
- A `DELETE` is immediately reflected — a subsequent `GET` returns `NoSuchKey`, not a stale copy.

**What is not covered by this guarantee** (read these as the actual edges of the mechanism, not footnotes):

- **Concurrent writers to the same key**: S3 has no locking. If two clients `PUT` the same key concurrently, S3 does not block or serialize them cooperatively — whichever request S3 finishes processing last wins, and the other's write is silently overwritten with no error to either caller. Consistency here means "the next reader sees *a* complete, uncorrupted object," not "writes are ordered the way you intended."
- **Cross-key atomicity**: there is no multi-key transaction. This is precisely why Iceberg (`data-formats/apache-iceberg.md`) and Delta Lake (`data-formats/delta-lake.md`) exist as separate systems layered on top of S3 — see the Gotchas section below.
- **Bucket-level configuration changes** (enabling Versioning, deleting a bucket, changing bucket policy) remain **eventually consistent** — e.g., a newly deleted bucket can still appear in `ListBuckets` briefly, and newly enabled Versioning needs a short propagation window. This is a genuinely separate, smaller carve-out from object-level consistency.
- **Cross-region replication (CRR)** is a distinct, inherently asynchronous feature — replicated copies in a destination region lag the source by however long replication takes; this is not covered by (and does not contradict) the same-region strong-consistency guarantee.
- **CloudFront** (or any CDN in front of S3) has its own cache TTL and invalidation model, entirely independent of S3's consistency guarantee. A CloudFront distribution can serve a stale cached response long after the underlying S3 object changed — hitting S3 directly is what the strong-consistency guarantee actually covers.

Verify all of this yourself in one shell session — write, overwrite, and delete, checking after each step, with no retry loop or sleep needed:

```bash
# 1. New object — read-after-write
echo '{"id":1}' > obj.json
aws s3api put-object --bucket my-bucket --key test/obj.json --body obj.json
aws s3api get-object --bucket my-bucket --key test/obj.json /dev/stdout
# → returns {"id":1} immediately, zero retry needed

# 2. Overwrite the SAME key — this is the case that was eventually consistent pre-Dec-2020
echo '{"id":2}' > obj.json
aws s3api put-object --bucket my-bucket --key test/obj.json --body obj.json
aws s3api get-object --bucket my-bucket --key test/obj.json /dev/stdout
# → returns {"id":2}, not the stale {"id":1} — this exact case is what the Dec 2020 change fixed

# 3. LIST immediately reflects the write
aws s3api list-objects-v2 --bucket my-bucket --prefix test/ --query 'Contents[].Key'
# → ["test/obj.json"]

# 4. DELETE is immediately reflected
aws s3api delete-object --bucket my-bucket --key test/obj.json
aws s3api get-object --bucket my-bucket --key test/obj.json /dev/stdout
# → An error occurred (NoSuchKey) — no stale-read window
```

This mechanism is why the resource-layer table above can say the network row is "unconditionally in the hot path but reliably correct" — engines that lean on S3 for correctness (Iceberg's atomic pointer swap to a new metadata JSON, Delta's `_delta_log` commit) can trust that once their commit-marking write returns success, every subsequent reader sees it, with no need to build their own quorum-read workaround the way a genuinely eventually-consistent store (early DynamoDB, S3 pre-2020) would have required. See `distributed-systems/consistency-models.md` for where this sits on the linearizability spectrum generally.

## High-to-Low Walkthrough: Writing and Reading a Parquet File

Trace one realistic operation end to end: a Spark/DuckDB job writes a Parquet file, a downstream query engine (DuckDB) reads it back with a footer-first access pattern.

```
aws s3api put-object (upload orders.parquet)
      │
      ▼
HTTP PUT to https://my-bucket.s3.amazonaws.com/warehouse/orders/data/part-00001.parquet
      │        body = raw Parquet bytes, Content-MD5 / checksum header for integrity
      ▼
S3 request router → partition owning this key's prefix range
      │        (S3 partitions the flat keyspace internally by key-range;
      │         "warehouse/orders/data/" is one or more partitions depending on
      │         request volume — see Deep Internals below)
      ▼
Durable write: object erasure-coded/replicated across ≥3 AZs (S3-internal,
invisible to caller) → 200 OK returned to caller ONLY once durable
      │
      ▼
Immediate aws s3api head-object / get-object from ANY client, ANY region-local
endpoint → strongly consistent, sees the new object, no propagation delay
      │
      ▼
Downstream reader (DuckDB) does NOT read the file start-to-end — it does a
footer-first range GET:
   1. HEAD (or a small range GET of the last ~8 bytes) to get file length
   2. Range GET of the last N KB → Parquet footer (schema + row-group offsets)
   3. Range GET(s) of only the column chunks / pages needed for the query's
      projected columns and predicate-matched row groups
```

Literal commands for every step:

```bash
# Upload
aws s3api put-object \
  --bucket my-bucket \
  --key warehouse/orders/data/part-00001.parquet \
  --body ./part-00001.parquet \
  --checksum-algorithm CRC32C

# Verify read-after-write with HEAD (metadata only, no body transfer — cheap existence/size check)
aws s3api head-object --bucket my-bucket --key warehouse/orders/data/part-00001.parquet
# {
#   "ContentLength": 52428800,
#   "ContentType": "application/octet-stream",
#   "ETag": "\"9bd8a...\"",
#   "LastModified": "2026-09-13T18:04:11+00:00"
# }

# List the prefix — this is a real network call to S3's LIST API, not a filesystem readdir
aws s3api list-objects-v2 \
  --bucket my-bucket \
  --prefix warehouse/orders/data/ \
  --query 'Contents[].{Key:Key,Size:Size}'

# Footer-first range GET — fetch only the last 64KB, where the Parquet footer lives
aws s3api get-object \
  --bucket my-bucket \
  --key warehouse/orders/data/part-00001.parquet \
  --range bytes=52363264-52428799 \
  footer.bin
# Content-Range in the response confirms the server honored the byte range:
# "ContentRange": "bytes 52363264-52428799/52428800"

# Then a targeted range GET for just the column chunk the query needs, using the
# byte offsets Parquet's own footer (data-formats/parquet.md) just gave you:
aws s3api get-object \
  --bucket my-bucket \
  --key warehouse/orders/data/part-00001.parquet \
  --range bytes=1048576-2097151 \
  column_chunk.bin
```

This is exactly what DuckDB's `httpfs` extension and Spark's S3A connector are doing under the hood when they read a Parquet file "lazily" — see `query-engines/duckdb.md`'s HTTPFS pushdown section and `data-formats/parquet.md`'s footer/page-index sections for what determines *which* byte ranges get requested; this doc is what those ranges look like as literal HTTP.

## Deep Internals

### S3 Is Not a Filesystem: Flat Keys, Not Paths

Every key in a bucket (`warehouse/orders/data/part-00001.parquet`) is one opaque string. The `/` characters are not directory separators to S3 — they are just characters in the key that the console and CLI tools (`aws s3 ls`, the S3 console's folder view) *interpret* as a hierarchy for display. There is no directory object, no inode, and critically: **no atomic rename**.

```bash
# This "looks like" a directory listing but is really a prefix-filtered LIST scan:
aws s3api list-objects-v2 --bucket my-bucket --prefix warehouse/orders/ --delimiter /
# CommonPrefixes in the response is S3 pretending there are subdirectories:
# {
#   "CommonPrefixes": [
#     {"Prefix": "warehouse/orders/data/"},
#     {"Prefix": "warehouse/orders/metadata/"}
#   ]
# }
```

"Renaming a folder" in the AWS CLI (`aws s3 mv s3://bucket/old-prefix/ s3://bucket/new-prefix/ --recursive`) is **not** one operation — it is a `COPY` of every single object under that prefix to a new key, followed by a `DELETE` of every original object:

```bash
# What "aws s3 mv --recursive" actually issues, per object, under the hood —
# there is no server-side rename primitive:
aws s3api copy-object --bucket my-bucket \
  --copy-source my-bucket/old-prefix/file1.parquet \
  --key new-prefix/file1.parquet
aws s3api delete-object --bucket my-bucket --key old-prefix/file1.parquet
# ...repeated once per object. For N objects: N copies + N deletes, non-atomic
# as a whole — a crash/failure partway through leaves both old and new prefixes
# in an inconsistent, partially-migrated state, with no rollback.
```

This single fact — no atomic multi-object rename, no atomic "swap this pointer" primitive at the object-store layer — is *exactly why* Iceberg and Delta Lake exist as separate metadata layers rather than just being "Parquet files in folders." Both formats solve atomicity by writing a **new, immutable metadata file** (Iceberg's next `vN.metadata.json`, Delta's next `_delta_log/000...N.json`) and then doing a **single atomic operation at the catalog layer** (a conditional pointer update, not an S3-native rename) to make that new metadata file "current." See `data-formats/apache-iceberg.md`'s snapshot/manifest-tree section and `data-formats/delta-lake.md`'s optimistic concurrency section — both are, at the storage layer, working around precisely the gap described in this paragraph.

### Multipart Upload

AWS recommends multipart upload once an object reaches **100 MB**; it becomes mandatory above 5 GB (the max size for a single, non-multipart `PUT`). The limits:

| Limit | Value |
|---|---|
| Max object size, single PUT | 5 GB |
| Max object size, multipart | 5 TiB per part-size ceiling × 10,000 parts → **48.8 TiB** theoretical max |
| Max parts per upload | 10,000 |
| Part size | 5 MiB – 5 GiB (last part may be smaller than 5 MiB) |
| AWS CLI default `multipart_threshold` / `multipart_chunksize` | 8 MB / 8 MB (configurable) |

Multipart upload exists for two reasons: it lets a client upload parts **in parallel** (throughput scales with concurrency rather than being capped by one TCP connection's single-stream speed), and it lets an interrupted upload **resume from the last completed part** instead of restarting a multi-GB transfer from byte zero.

```bash
# Initiate
UPLOAD_ID=$(aws s3api create-multipart-upload \
  --bucket my-bucket --key warehouse/orders/data/big-file.parquet \
  --query 'UploadId' --output text)

# Upload parts (can run these concurrently, e.g. via xargs -P or parallel)
aws s3api upload-part --bucket my-bucket --key warehouse/orders/data/big-file.parquet \
  --part-number 1 --upload-id "$UPLOAD_ID" --body part1.bin
aws s3api upload-part --bucket my-bucket --key warehouse/orders/data/big-file.parquet \
  --part-number 2 --upload-id "$UPLOAD_ID" --body part2.bin

# Each upload-part response returns an ETag — you need all of them to complete:
aws s3api list-parts --bucket my-bucket --key warehouse/orders/data/big-file.parquet \
  --upload-id "$UPLOAD_ID"

# Complete (assembles parts server-side; requires the exact ETag list)
aws s3api complete-multipart-upload --bucket my-bucket \
  --key warehouse/orders/data/big-file.parquet --upload-id "$UPLOAD_ID" \
  --multipart-upload '{"Parts":[{"ETag":"\"abc\"","PartNumber":1},{"ETag":"\"def\"","PartNumber":2}]}'
```

**The specific failure mode this doc's brief calls out**: if a client crashes, times out, or simply never calls `complete-multipart-upload` or `abort-multipart-upload`, the already-uploaded parts are **not visible as an object** (no key appears in `LIST`) but **are billed as storage indefinitely**, silently, forever, until explicitly aborted or removed by a lifecycle rule:

```bash
# Find abandoned multipart uploads — these do NOT show up in list-objects-v2 at all
aws s3api list-multipart-uploads --bucket my-bucket
# {
#   "Uploads": [
#     {"Key": "warehouse/orders/data/big-file.parquet",
#      "UploadId": "2~AbCdEf...",
#      "Initiated": "2026-06-01T10:00:00Z"}
#   ]
# }

# Manually abort one
aws s3api abort-multipart-upload --bucket my-bucket \
  --key warehouse/orders/data/big-file.parquet --upload-id "2~AbCdEf..."
```

The durable fix is a bucket lifecycle rule using the `AbortIncompleteMultipartUpload` action, so this never depends on someone remembering to check:

```bash
cat > lifecycle.json <<'EOF'
{
  "Rules": [{
    "ID": "abort-stale-multipart",
    "Status": "Enabled",
    "Filter": {},
    "AbortIncompleteMultipartUpload": {"DaysAfterInitiation": 7}
  }]
}
EOF
aws s3api put-bucket-lifecycle-configuration --bucket my-bucket \
  --lifecycle-configuration file://lifecycle.json
```

### Key Prefix Partitioning and Request Rate

Since a **July 2018** change, S3 automatically partitions a bucket's keyspace by prefix ranges as request volume grows, and no longer requires manually hash-randomizing key prefixes for scaling — this predates most current engineering advice you'll find and supersedes the once-standard "reverse your timestamp" / "prepend a hex hash" recommendations for high-throughput key design.

Current documented per-prefix rate targets before you should expect to actively manage distribution (AWS "Performance design patterns for Amazon S3," 2026):

- **3,500 PUT/COPY/POST/DELETE requests/sec per prefix**
- **5,500 GET/HEAD requests/sec per prefix**
- No cap on the number of prefixes per bucket — these numbers scale roughly linearly with the number of distinct, actively-used prefixes.

Two nuances the "just don't worry about it, it's 2018-solved" narrative glosses over:

1. S3's auto-scaling is **gradual, not instantaneous** — a sudden spike against a single, narrow prefix (e.g., a batch job hammering one `dt=2026-09-13/` partition) can still produce `503 Slow Down` responses while S3's internal partitioning catches up, even though it will settle once sustained load establishes a pattern.
2. AWS's *current* docs still list "distribute the workload across multiple prefixes" as an active mitigation for workloads that sustain rates above the numbers above — this is not identical to the old blanket "always hash your keys" advice, but it means prefix design still matters for genuinely hot, narrow access patterns (e.g., a single Hive-style partition receiving a flash-crowd of concurrent readers).

Check for throttling directly, and confirm which prefix a hot dataset actually lives under:

```bash
# CloudWatch request-rate/error metrics are the way to actually observe this in
# production rather than guess — check for 5xxErrors on the bucket's request metrics
aws cloudwatch get-metric-statistics \
  --namespace AWS/S3 --metric-name 5xxErrors \
  --dimensions Name=BucketName,Value=my-bucket Name=FilterId,Value=EntireBucket \
  --start-time 2026-09-13T00:00:00Z --end-time 2026-09-13T23:59:59Z \
  --period 3600 --statistics Sum
```

For a Hive/Iceberg-style data lake table, this is exactly why partition layout (`data-formats/apache-iceberg.md`'s partition evolution, `data-formats/z-ordering.md`) is not purely a query-pruning decision — it also determines how many distinct S3 key prefixes your writers and readers spread load across during a hot ingestion window.

### Storage Classes for Data Lake Use

| Class | Retrieval latency | Typical data-lake use |
|---|---|---|
| S3 Standard | Milliseconds, always available | Active/hot tables, current Iceberg/Delta snapshots |
| S3 Intelligent-Tiering | Milliseconds (Frequent/Infrequent Access tiers, automatic); optional opt-in Archive tiers below | Tables with unpredictable/unknown access patterns — avoids manually classifying cold data |
| S3 Glacier Instant Retrieval | Milliseconds | Rarely-accessed but latency-sensitive-when-accessed data (compliance data that's occasionally queried live) |
| S3 Glacier Flexible Retrieval | Minutes (expedited) to 3–5 hours (standard) | Cold historical partitions, quarterly/annual reprocessing |
| S3 Glacier Deep Archive | 12–48 hours | Long-term compliance retention, effectively never queried live |

Intelligent-Tiering's automatic behavior only covers the two low-latency tiers by default; its Archive Access and Deep Archive Access tiers are **opt-in configuration**, not something that happens automatically just by enabling Intelligent-Tiering — worth checking explicitly rather than assuming cold data auto-archives to Glacier-equivalent tiers.

```bash
# Apply Intelligent-Tiering with optional archive tiers opted in
aws s3api put-bucket-intelligent-tiering-configuration \
  --bucket my-bucket --id archive-cold-partitions \
  --intelligent-tiering-configuration '{
    "Id": "archive-cold-partitions",
    "Status": "Enabled",
    "Tierings": [
      {"Days": 90, "AccessTier": "ARCHIVE_ACCESS"},
      {"Days": 180, "AccessTier": "DEEP_ARCHIVE_ACCESS"}
    ]
  }'

# A lifecycle rule transitioning old Iceberg/Delta snapshot files to Glacier —
# note this must never touch CURRENT table data/metadata, only files a
# retention/expiry process has already confirmed are unreferenced by any
# live snapshot (see the versioning gotcha below)
aws s3api put-bucket-lifecycle-configuration --bucket my-bucket \
  --lifecycle-configuration '{
    "Rules": [{
      "ID": "archive-cold-data",
      "Status": "Enabled",
      "Filter": {"Prefix": "warehouse/orders/data/"},
      "Transitions": [{"Days": 90, "StorageClass": "GLACIER"}]
    }]
  }'
```

### S3 Express One Zone

Launched at re:Invent, GA in **late 2023**. It is a distinct, higher-performance storage class: data is stored redundantly across multiple devices but **within a single Availability Zone**, not S3 Standard's multi-AZ redundancy — a deliberate durability/availability tradeoff traded for latency. AWS's current (2026) documentation describes it as delivering **single-digit-millisecond** data access, "up to 10x faster" than S3 Standard, with roughly 80% lower per-request cost than S3 Standard. (Earlier 2023 launch messaging cited different, more modest improvement figures — use the current docs' numbers, not the launch-week press release, if precision matters.)

```bash
# S3 Express One Zone buckets are "directory buckets" — distinct API surface,
# created in a single AZ, named with an --az-id suffix
aws s3api create-bucket --bucket my-fast-bucket--use1-az4--x-s3 \
  --region us-east-1 --create-bucket-configuration \
  '{"Location":{"Type":"AvailabilityZone","Name":"use1-az4"},"Bucket":{"Type":"Directory","DataRedundancy":"SingleAvailabilityZone"}}'
```

Relevance to analytics workloads: positioned for latency-sensitive, high-throughput interactive query and ML training scenarios where compute is co-located in the same AZ — not typically the durable system-of-record tier for a full lakehouse (S3 Standard remains that), but a viable fast working-set tier in front of it for engines like DuckDB/Spark doing repeated scans against a hot working set.

## Comparative: vs. HDFS, vs. Other Object Stores

**vs. HDFS** (cross-referencing `storage/hadoop.md` directly): HDFS's entire design bet is that co-locating compute and replicated storage lets a scheduler place a task on a node that already holds the data, making most reads free of network cost. S3 gives up that bet entirely — there is no "local" replica from the client's perspective, full stop, so the network row in this doc's resource-layer table is unconditionally in the hot path for every single read, whereas HDFS's equivalent table shows the network row as something the whole system is engineered to *avoid* hitting. In exchange, S3 offers what HDFS structurally cannot: storage that scales and is billed independently of any compute cluster's node count, 11-nines durability the client never manages, and no NameNode-style single metadata service to capacity-plan around. `storage/hadoop.md`'s claim that "the modern lakehouse pattern explicitly trades away HDFS's locality-driven network savings for the operational simplicity of not co-managing a compute cluster's disks as your storage tier" is directly justified by everything in this doc's resource-layer map and Deep Internals sections: S3's durability is invisible/free-to-the-client, its consistency model (post-2020) is strong enough for Iceberg/Delta to build correctness on top of, and its cost model (storage classes + lifecycle) decouples cold-data economics from compute cluster sizing — none of which HDFS's colocated model offers, at the structural cost of making every read a network call.

**vs. GCS / Azure Blob / MinIO**: S3's `PUT`/`GET`/`HEAD`/`DELETE`/`LIST` request model and its signed-URL (SigV4) authentication scheme have become the de facto API that most other object stores implement compatibility shims for, rather than each store having a genuinely distinct protocol. Google Cloud Storage exposes a native JSON/XML API but also ships an S3-compatible XML API surface for migration convenience; Azure Blob Storage's native API (`PUT` with different header conventions, containers instead of buckets) is not S3-API-compatible out of the box, though most data-lake engines (Spark, Trino, DuckDB) abstract this behind a filesystem connector layer (`abfss://` vs `s3://` vs `gs://`) so the difference is mostly invisible above the connector. MinIO is the most direct S3-API-compatible option — it implements the S3 REST API closely enough that `aws s3api` commands and the AWS SDK work against a MinIO endpoint largely unmodified (just point `--endpoint-url` at the MinIO server), making it the common choice for on-prem/self-hosted S3-API-compatible storage. None of GCS, Azure Blob, or MinIO change the fundamental architectural facts in this doc (flat keyspace, no cross-key transactions, no client-visible locality) — the API surface differs at the margins, the object-storage model itself does not.

```bash
# aws CLI against a MinIO endpoint — same commands, different endpoint
aws --endpoint-url http://minio.local:9000 s3api list-objects-v2 --bucket my-bucket
```

## Key Gotchas

- **"S3 is a filesystem" mental model causes real bugs**: there is no atomic rename. `aws s3 mv --recursive` on a prefix is N copies + N deletes, non-atomic as a whole, and can leave a table in an inconsistent state if it fails partway. This is precisely why Iceberg (`data-formats/apache-iceberg.md`) and Delta Lake (`data-formats/delta-lake.md`) never rely on renaming data files into place — they write new immutable files and atomically swap a metadata pointer instead, at the catalog layer, working around the exact gap this doc describes.
- **Abandoned multipart uploads silently bill for storage forever**: an interrupted upload that never calls `complete-multipart-upload` or `abort-multipart-upload` leaves parts that don't appear in any object listing but are billed indefinitely. Check with `aws s3api list-multipart-uploads`; prevent it structurally with a lifecycle rule's `AbortIncompleteMultipartUpload` action (7 days is a common default), not by relying on manual cleanup.
- **A single hot, unpartitioned prefix under high request rate gets throttled (`503 Slow Down`)**: S3's per-prefix auto-scaling (3,500 write-type req/s, 5,500 read-type req/s per prefix, as of current AWS docs) is gradual, not instantaneous — a sudden flash-crowd against one narrow prefix (e.g., a Hive partition every worker hits simultaneously at ingestion time) can throttle even though sustained load at that same rate would eventually be absorbed. Spread hot access across more prefixes if you control the key layout.
- **"S3 is eventually consistent" is an outdated claim you will still see repeated** in older blog posts, some third-party tutorials, and even stale internal docs — this was true for overwrite `PUT`s and `LIST`s before December 2020, and is false for any AWS commercial region today. If a doc, wiki page, or teammate asserts S3 is eventually consistent for basic object operations without a date qualifier, that claim is either about pre-2020 S3, about a genuinely separate carve-out (bucket configuration propagation, cross-region replication lag, CDN caching), or simply wrong — verify which.
- **Versioning + misconfigured lifecycle rules silently multiply storage cost**: enabling bucket Versioning means every overwrite `PUT` or `DELETE` keeps the prior version around as a separate billed object, rather than replacing it. Without a lifecycle rule that expires noncurrent versions, tables that get rewritten frequently (a Delta/Iceberg CoW table doing full-file rewrites on every compaction, for instance) can accumulate old-version storage cost far exceeding the current live dataset's size, with no forcing function to notice unless someone runs `list-object-versions` or checks the storage-cost breakdown.

  ```bash
  # Check for accumulated noncurrent versions (billed but invisible in a normal LIST)
  aws s3api list-object-versions --bucket my-bucket --prefix warehouse/orders/ \
  ```
